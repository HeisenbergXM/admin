### 🔴 问题 1：`toggleDictTypeStatus` / `toggleDictItemStatus` 存在并发覆盖风险

| 字段 | 值 |
|------|-----|
| **文件** | `DictServiceImpl.java:100-108`（toggleDictTypeStatus）、`:156-164`（toggleDictItemStatus） |
| **类型** | 并发 BUG（可能的数据丢失） |

**问题描述**：两个方法使用"先查后改"模式：

```java
DictType dictType = dictTypeMapper.selectById(id);  // 查到全部字段
dictType.setStatus(status);                          // 只改了 status
dictTypeMapper.updateById(dictType);                 // 把全部字段写回！
```

MyBatis-Plus 的 `updateById` 默认将所有非 null 字段写入 SET 子句。如果两个请求几乎同时到达：

1. 请求 A（管理员）调用 `updateDictType` 修改 `dictName` → `dictName="新发票状态"`
2. 同一瞬间请求 B 调用 `toggleDictTypeStatus(1, 0)` 
3. B 的 `selectById` 拿到了**旧**的 `dictName`
4. B 仅修改 `status`，然后 `updateById` 写回——**覆盖了** A 刚刚修改的 `dictName`

**修复方案**：改用 `LambdaUpdateWrapper` 只更新 status 字段，避免读-改-写三步：

```java
public void toggleDictTypeStatus(Long id, Integer status) {
    if (status == null || (status != 0 && status != 1)) {
        throw new BusinessException(ErrorCode.BAD_REQUEST);
    }
    dictTypeMapper.update(null, new LambdaUpdateWrapper<DictType>()
            .eq(DictType::getId, id)
            .set(DictType::getStatus, status));
}
```

`toggleDictItemStatus` 同理：

```java
public void toggleDictItemStatus(Long id, Integer status) {
    if (status == null || (status != 0 && status != 1)) {
        throw new BusinessException(ErrorCode.BAD_REQUEST);
    }
    dictItemMapper.update(null, new LambdaUpdateWrapper<DictItem>()
            .eq(DictItem::getId, id)
            .set(DictItem::getStatus, status));
}
```

**优先级**：🔴 **建议在阶段 2 开始前修复**

### 🟠 问题 2：多处异常使用 `new BusinessException(400, "...")`，与 ErrorCode 枚举风格不一致

| 字段 | 值 |
|------|-----|
| **文件** | `DictServiceImpl.java` |
| **类型** | 代码规范/一致性 |

**问题描述**：`createDictType` 使用 `ErrorCode.DICT_CODE_EXISTS`，`deleteDictType` 使用 `ErrorCode.DICT_TYPE_HAS_ITEMS`——但以下 4 处使用了硬编码的 `400`：

| 方法 | 当前代码 | 建议使用的 ErrorCode |
|------|---------|---------------------|
| `updateDictType:77` | `new BusinessException(400, "字典类型不存在")` | `DICT_TYPE_NOT_FOUND`（需新增） |
| `updateDictItem:132` | `new BusinessException(400, "字典项 ID 不能为空")` | `DICT_ITEM_ID_REQUIRED`（需新增） |
| `updateDictItem:135` | `new BusinessException(400, "字典项不存在")` | `DICT_ITEM_NOT_FOUND`（需新增） |
| `toggleDictTypeStatus:103` | `new BusinessException(400, "字典类型不存在")` | `DICT_TYPE_NOT_FOUND` |
| `toggleDictItemStatus:159` | `new BusinessException(400, "字典项不存在")` | `DICT_ITEM_NOT_FOUND` |

硬编码 `400` 的问题：前端接错时只能看到"参数错误"，无法区分具体场景做国际化或提示用户。

**修复方案**：在 `ErrorCode.java` 中新增以下枚举值：

```java
DICT_TYPE_NOT_FOUND(6015, "字典类型不存在"),
DICT_ITEM_NOT_FOUND(6016, "字典项不存在"),
DICT_ITEM_ID_REQUIRED(6017, "字典项 ID 不能为空"),
```

然后逐处替换。

**优先级**：🟠 **建议修复**

### 🟠 问题 3：`deleteDictItem` 未校验记录是否存在

| 字段 | 值 |
|------|-----|
| **文件** | `DictServiceImpl.java:150-153` |
| **类型** | 逻辑完整性/健壮性 |

**问题描述**：

```java
@Override
@Transactional
public void deleteDictItem(Long id) {
    dictItemMapper.deleteById(id);  // 不存在的 ID 也返回成功
}
```

与 `updateDictItem` 先查后抛的风格不一致。`deleteById` 对不存在的 ID 不影响任何行，Controller 仍返回 `Result.success()`。前端无法区分"删除成功"和"该记录已被他人删除"。

**修复方案**：

```java
public void deleteDictItem(Long id) {
    DictItem item = dictItemMapper.selectById(id);
    if (item == null) {
        throw new BusinessException(ErrorCode.DICT_ITEM_NOT_FOUND);
    }
    dictItemMapper.deleteById(id);
}
```

**优先级**：🟠 **建议修复**

### 🟡 问题 4：`toggleDictTypeStatus` / `toggleDictItemStatus` 未校验 status 参数合法性

| 字段 | 值 |
|------|-----|
| **文件** | `DictController.java:78-82`, `:126-130` |
| **类型** | 安全/健壮性 |

**问题描述**：

```java
public Result<Void> toggleTypeStatus(@PathVariable Long id,
                                     @RequestBody Map<String, Integer> body) {
    dictService.toggleDictTypeStatus(id, body.get("status"));
```

如果请求体 `{"xxx": 1}` 中不包含 `status` 字段，`body.get("status")` 返回 `null`，Service 层 `dictType.setStatus(null)` → DB 中该字段被设为 `NULL`，破坏 `status` 只能为 0 或 1 的业务约束。

**修复方案**：在 Service 方法入口处校验：

```java
if (status == null || (status != 0 && status != 1)) {
    throw new BusinessException(ErrorCode.BAD_REQUEST);
}
```

或改为使用 `@RequestBody @Valid StatusUpdateRequest` DTO（含 `@NotNull` + `@Min(0)` + `@Max(1)` 校验注解），避免直接使用 `Map`。

**优先级**：🟡 **按需修复**

### 🟡 问题 5：`getItemsByCode` 对不存在的 dictCode 无法区分"类型不存在"和"类型为空"

| 字段 | 值 |
|------|-----|
| **文件** | `DictServiceImpl.java:167-180` |
| **类型** | 接口可维护性 |

**问题描述**：

```java
DictType dictType = dictTypeMapper.selectOne(...);
if (dictType == null) {
    return List.of();  // 和"该类型下没有字典项"返回一致
}
```

当 `dictCode` 写错时（如 `"invoic_status"` 误写成 `"invoice_staus"`），静默返回空列表。前端下拉直接显示空。排查问题时无从得知是编码错了还是字典确实为空。

**修复方案（二选一）**：
1. 编码不存在时抛出 `DICT_TYPE_NOT_FOUND` 异常
2. 在响应中增加标识字段（如 `typeExists: false`），但这涉及修改返回结构

建议使用方案 1，因为前端下拉传入的 dictCode 通常是固定的，如果返回 404 说明代码配置有误，报错比静默处理更有利于发现问题。

**优先级**：🟡 **按需修复**

### 🟡 问题 6：`DictTypeUpdateRequest` 不允许修改 `dictCode`

| 字段 | 值 |
|------|-----|
| **文件** | `DictTypeUpdateRequest.java` |
| **类型** | 功能完整性/设计决策 |

**问题描述**：UpdateRequest 只有 `dictName`、`status`、`remark` 三个字段，不包括 `dictCode`。字典编码一旦创建即不可修改。

**分析**：如果字典编码是业务语义标识（如 `invoice_status`），不可修改是合理的设计，避免连锁修改前端的硬编码引用。但如果仅仅是管理需求变更，需要人工改数据库，不够灵活。

**建议**：确认产品需求中是否有修改字典编码的场景。如果没有，保持现状并记录为有意识的设计约束。如果未来需要修改，需同时校验新编码的唯一性。

**优先级**：🟡 **确认需求后决定**
