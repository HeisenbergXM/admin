# 设计文档 — 运输管理改造：按 VIN 单车维护物流信息

- **Spec ID**：D00003
- **需求类型**：优化需求
- **状态**：待批准（pending_approval）
- **派生自**：[D00001 车辆全生命周期管理系统](../../D00001/specs/design.md)

---

## 1. 概述

D00001 的运输管理采用「单据驱动批量流转」，是全系统里唯一不走「每阶段一张 `t_veh_*` 阶段表」的例外：

- 车厂→中转仓库用 **运输单 `t_transport_order` + 明细 `t_transport_order_item`**（整单确认）；
- 中转仓库→经销商用 **发车清单 `t_dispatch_list` → 行车路单 `t_waybill` → 经销商行 `t_waybill_dealer` → 经销商行-VIN `t_waybill_dealer_vin`**（按经销商行确认签收）。

本次改造**新增一套以单车为粒度的物流实现**：物流两段回归标准阶段表模式，改为**按 VIN 单车维护**——与生产、销售分配、收款、上牌等阶段完全同构。功能显著简化：不再组织任何批量单据，直接对单辆车维护其物流字段并逐车确认推进。

**核心原则——两套共存、各自独立、互不影响：** 旧的单据式运输管理（D00001 的运输单 / 发车清单 / 行车路单 / 经销商行，共 6 张表及其后端代码/API）**全部保留不删**，仅**停用**——通过隐藏/移除其菜单入口实现，旧代码与 API 仍在，日后可快速恢复。运输管理的**可见入口切换**为新的按 VIN 功能。两套共享同一 `t_vehicle` 与同一套生命周期卡控；由于旧入口已停用，实际只有新功能在推进车辆生命周期，二者不冲突。

### 1.1 目标

- 物流两段（入库、配送）以**单辆车（VIN）**为操作单位维护，运输管理入口切换为新功能。
- 物流两段新增标准阶段表：`t_veh_inbound`（入库）、`t_veh_delivery`（配送），与其他 `t_veh_*` 表同构。
- **保留** D00001 的「草稿→确认锁定→推进 lifecycle_stage」机制，仅将确认粒度从「单据/单据行」改为「单车」。
- 旧单据式运输管理**保留但停用**（表/代码/API 不删，仅隐藏菜单入口）。
- 生命周期 7 阶段顺序与卡控规则**完全不变**。

### 1.2 非目标（本期不含）

- 不改动生产、销售、财务、上牌等其他阶段的任何设计。
- **不删除**旧单据式运输管理的表、后端代码或 API（仅停用其入口）。
- 不引入中转仓库实体/主数据（沿用 D00001，仅记录到仓日期等字段）。
- 不修改 D00001 需求文档本身（D00001 保持现状）。
- 不提供批量导入/导出（除全景视图外，沿用 D00001 的口径）。

### 1.3 与 D00001 的关系（两套共存）

| 方面 | 旧：单据式（D00001，保留但停用） | 新：按 VIN 单车（D00003，启用为唯一入口） |
|------|-------------------------------------|--------------------------------------------|
| 车厂→中转仓库 | 运输单（1 单 N 车）整单确认 | **按 VIN 单车**维护入库信息、单车确认 |
| 中转仓库→经销商 | 发车清单→行车路单→经销商行，按行确认 | **按 VIN 单车**维护配送信息、单车确认 |
| 数据表 | `t_transport_order`(+item)、`t_dispatch_list`/`t_waybill`/`t_waybill_dealer`(+vin) 共 6 张——**保留不删** | `t_veh_inbound`、`t_veh_delivery` 共 2 张阶段表——**新增** |
| 后端代码/API | **保留可用**（日后可恢复入口） | 新增 |
| 菜单入口 | **隐藏/移除**（停用） | **启用**（运输管理唯一可见入口） |
| 确认机制 | 草稿→确认锁定→推进（作用于单据/单据行） | 草稿→确认锁定→推进（作用于单车），机制不变 |
| 生命周期阶段 | 7 阶段严格卡控 | **共享同一 t_vehicle 与卡控，完全一致** |
| 中转仓库实体 | 无（仅记到仓日期） | 无（沿用） |

> D00001 需求文档不做任何修改。两套运输管理并存、互不影响、各自独立：旧套保留代码/表仅停用入口，新套上线为运输管理的实际入口。其余模块（生产/销售/财务/上牌/主数据/系统管理/全景视图）全部沿用 D00001。

## 3. 受影响的功能模块

仅「运输管理」模块发生变化：新增一套按 VIN 单车维护的功能并切换为可见入口，旧单据式功能保留但隐藏入口。模块在菜单中的位置与归属不变：

```
运输管理（可见入口 = 新按 VIN 功能）
├── 车厂到中转仓库   （新）按 VIN 单车维护入库信息 → 单车确认 → 推进 PENDING_ALLOCATION
└── 中转仓库到经销商 （新）按 VIN 单车维护配送信息 → 单车确认 → 推进 PENDING_REGISTRATION

运输管理（旧单据式，保留但停用 / 隐藏入口）
├── 车厂到中转仓库   （旧）运输单批量整单确认        —— 代码/表/API 保留，菜单入口隐藏
└── 中转仓库到经销商 （旧）发车清单→行车路单→经销商行 —— 代码/表/API 保留，菜单入口隐藏
```

> 两套并存、各自独立、互不影响。旧套仅隐藏菜单入口，后端代码与 API 保留可用，日后可快速恢复。其余模块（系统管理 / 主数据管理 / 生产管理 / 销售管理 / 财务管理 / 车辆全景视图）**不变**。

## 4. 生命周期状态机（不变）

生命周期 7 阶段、顺序、卡控规则与 D00001 **完全一致**，仅物流两段的“推进触发方式”从单据确认改为单车确认：

```
[0] PENDING_OFFLINE        草稿（新录入）
[1] PENDING_INBOUND        待入库
        │ 物流专员按 VIN 确认车厂→中转仓库入库后进入
        ▼
[2] PENDING_ALLOCATION     待分配
        ...（销售/财务各阶段不变）...
[5] PENDING_DELIVERY       待配送
        │ 物流专员按 VIN 确认中转仓库→经销商配送签收后进入
        ▼
[6] PENDING_REGISTRATION   待上牌
[7] COMPLETED              已完结
```

### 4.1 卡控规则（物流两段，改为单车粒度）

| 操作 | 前置条件（车辆须处于的阶段） | 确认后推进 |
|------|------------------------------|-----------|
| 车厂→中转仓库 入库确认 | VIN 处于 `PENDING_INBOUND` | → `PENDING_ALLOCATION` |
| 中转仓库→经销商 配送签收确认 | VIN 处于 `PENDING_DELIVERY` 且已分配经销商 | → `PENDING_REGISTRATION` |

> 卡控前后端双重校验，后端为准（与 D00001 一致）。“未被其他运输单占用”“属于该经销商行”等**单据相关的占用/归属校验被移除**——单车维护不存在单据占用问题；配送阶段仍校验该车已在销售阶段分配了经销商。

## 5. 数据模型

### 5.1 保留的表（旧单据式，保留不删、仅停用功能）

以下 6 张单据式表**全部保留**（含其后端代码与 API），不做删除或结构变更，仅停用其菜单入口：

- `t_transport_order`、`t_transport_order_item`
- `t_dispatch_list`、`t_waybill`、`t_waybill_dealer`、`t_waybill_dealer_vin`

> 这些表与新增的 `t_veh_inbound`/`t_veh_delivery` **并存**。因旧入口停用，运行期不会有新数据写入旧表；已有存量数据（若有）原样保留。日后如需恢复旧单据式功能，恢复菜单入口即可。

### 5.2 新增阶段表（与其他 `t_veh_*` 同构，1:1 于 t_vehicle）

沿用 D00001 阶段表**统一公共字段**（6.3 节）：

```
id                主键
vehicle_id        FK t_vehicle（一辆车每阶段至多一条，1:1）
stage_status      draft（草稿，可改）/ confirmed（已确认，锁定）
confirmed_by      确认人        confirmed_at  确认时间
created_by        创建人        created_at    创建时间
updated_by        修改人        updated_at    修改时间
```

**① 入库 `t_veh_inbound`（车厂 → 中转仓库）** — 前置 `PENDING_INBOUND`，确认后置 `PENDING_ALLOCATION`

| 字段 | 说明 | Excel/来源 |
|------|------|-----------|
| saic_buy_off_date | SAIC buy off 日期 | O 列（原运输单明细逐车字段） |
| date_to_storage_yard | 到中转仓库日期 | P 列（原运输单表头字段，改为逐车） |
| remark2 | 备注2 | Q 列 |

**② 配送 `t_veh_delivery`（中转仓库 → 经销商）** — 前置 `PENDING_DELIVERY`，确认后置 `PENDING_REGISTRATION`

| 字段 | 说明 | Excel/来源 |
|------|------|-----------|
| etd_to_dealer | 发车日期 | AH 列 |
| eta_to_dealer | 预计到达日期 | AI 列 |
| trolly_type | 轿运车类型（4/6 units，可选） | AJ 列 |
| fully_load | 是否满载（可选） | AK 列 |
| received_date | 经销商签收日期 | AL 列 |
| delivery_status | 配送状态（字典 `delivery_status`） | AM 列 |
| remark7 | 备注7 | AN 列 |

> 说明：
> - 经销商**不在配送表冗余存储**——该车的经销商实时取自销售分配阶段 `t_veh_allocation.dealer_id`（配送阶段只读展示）。
> - `trolly_type`/`fully_load` 原属行车路单（一辆轿运车）；改为单车维护后作为该车的可选描述字段保留，不建轿运车实体。
> - 车型/颜色/年款等基本信息实时取 `t_vehicle` 与主数据，不冗余（与 D00001 一致）。

### 5.3 车辆主表 `t_vehicle`（不变）

`t_vehicle`（id/vin/lifecycle_stage + 审计字段）不变。物流两段的推进逻辑改为由 `t_veh_inbound`/`t_veh_delivery` 的单车确认触发，与其他阶段表一致。

## 6. 功能需求明细（运输管理，新增按 VIN 功能 + 旧功能停用）

### 6.1 车厂 → 中转仓库（按 VIN 单车维护入库）

- **待办列表**：列出所有处于 `PENDING_INBOUND` 的车辆（VIN + 车型/颜色/年款等基本信息），支持按 VIN/车型等多条件查询。
- **单车维护**：选中一辆车（或输入 VIN）进入入库信息维护，填写 `saic_buy_off_date`、`date_to_storage_yard`、`remark2`；`stage_status=draft` 期间可反复修改。
- **单车确认**：点「确认」→ 校验该 VIN 仍处 `PENDING_INBOUND` → 锁定入库记录、记录确认人/时间 → 主表 `lifecycle_stage` 推进 `PENDING_ALLOCATION`。确认后不可再改、不可重复确认。
- **无批量单据**：不再有运输单/明细/整单确认；每辆车独立维护、独立确认。（可选增强：提供多选后“批量确认”，逐车执行同一单车确认逻辑，非必需，列入开放问题。）

### 6.2 中转仓库 → 经销商（按 VIN 单车维护配送）

- **待办列表**：列出所有处于 `PENDING_DELIVERY` 的车辆（VIN + 基本信息 + 已分配经销商，只读带出），支持多条件查询。
- **单车维护**：选中一辆车进入配送信息维护，填写 `etd_to_dealer`、`eta_to_dealer`、`trolly_type`、`fully_load`、`received_date`、`delivery_status`、`remark7`；`draft` 期间可反复修改。
- **单车确认（签收）**：点「确认」→ 校验该 VIN 处 `PENDING_DELIVERY` 且已分配经销商 → 锁定配送记录、记录确认人/时间 → 主表 `lifecycle_stage` 推进 `PENDING_REGISTRATION`。确认后不可再改、不可重复确认。
- **无发车清单/行车路单/经销商行**：不再组织三层单据；每辆车独立维护、独立确认签收。

### 6.3 全景视图适配

车辆全景视图（业务主管）物流环节改为聚合**新的** `t_veh_inbound` 与 `t_veh_delivery` 两张阶段表，时间线呈现与其他阶段表一致。因新功能是运输管理的实际入口、旧套已停用，全景视图以新阶段表为准；旧单据表虽保留，但不再作为全景视图物流数据源（若存量旧数据需展示，作为可选增强，见开放问题）。

### 6.4 旧单据式功能停用（保留代码/表）

- 从菜单管理中**移除/隐藏**旧单据式运输管理（车厂到仓库运输单、仓库到经销商发车清单）的菜单项与路由入口。
- 旧单据式的后端 Controller/Service/Repository 与 6 张表**保留不动**，不删除、不改结构；API 仍可用但无前端入口触发。
- 与新功能共享同一 `t_vehicle` 与生命周期卡控；旧入口停用后仅新功能推进车辆生命周期，二者互不影响。
- 恢复策略：日后如需重新启用旧套，恢复其菜单入口即可，无需改动后端。

## 8. 隔离与不回归约束（实现方必须遵守）

本 spec 与旧单据式运输管理**共享同一 `t_vehicle` 主表与同一套生命周期卡控服务**。为保证「不影响之前任何与运输管理相关的功能、避免造成其它功能不可用」，实现时必须遵守以下约束——这是本设计的硬性要求，不是建议。

### 8.1 只增不改（新增优先，禁止就地改写共享逻辑）

- **数据库**：仅**新增** `t_veh_inbound`、`t_veh_delivery` 两张表。旧 6 张单据表**不删除、不改表结构、不改字段、不加破坏性约束**；`t_vehicle` 及其他 `t_veh_*` 表结构**不改动**。
- **后端代码**：新功能走**新的 Controller/Service/Repository**（如 `VehInboundService`/`VehDeliveryService`），**不修改**旧单据式的 `t_transport_order`/`t_dispatch_list` 等相关类与接口。
- **生命周期卡控服务**：新功能**复用现有卡控/确认通用机制**（阶段流转、前置校验、draft↔confirmed），只能以**调用/扩展**方式接入，**不得就地改写**该服务已有的方法签名与行为——因为旧套及其他阶段（生产/销售/财务/上牌）都依赖它。如需扩展，采用新增方法/新增枚举分支，保持既有分支不变。

### 8.2 共享资源的安全使用

- **生命周期阶段枚举**：`PENDING_INBOUND → PENDING_ALLOCATION`、`PENDING_DELIVERY → PENDING_REGISTRATION` 的目标阶段与旧套**完全相同**，不新增/不重命名阶段枚举值。新旧两套调用同一套流转，语义一致。
- **字典**：`delivery_status` 字典**复用**，不新建重复字典、不改动既有字典项编码。
- **经销商来源**：配送阶段经销商实时读取 `t_veh_allocation.dealer_id`（只读），不写回、不修改销售分配数据。
- **并发一致性**：一辆车在任一时刻只应有一套入口在推进（旧入口已停用）；卡控在确认时校验「VIN 处于对应前置阶段」，天然阻止重复推进（旧套若被临时恢复也受同一卡控保护，不会把已推进的车重复推进）。

### 8.3 停用旧入口的安全方式

- 停用仅通过**隐藏/移除菜单项与前端路由**实现（菜单管理层面），**不删除、不注释、不改动**旧后端代码与 API。
- 不得因停用旧入口而删除或修改旧套依赖的任何共享组件（卡控服务、字典、主数据、`t_vehicle`）。
- 恢复旧入口只需重新挂回菜单，无需回滚后端——以此验证「保留可恢复」。

### 8.4 回归验证（作为验收的一部分）

- 其他阶段功能（生产录入、销售分配、发票、收款、上牌、主数据、系统管理、全景视图）在本次改造后**行为不变**，须有回归确认。
- 若项目已有旧运输管理的自动化测试，**必须继续全部通过**；不得为让新功能通过而修改或删除旧测试的断言。
- 旧套后端 API（即使前端无入口）**仍可被直接调用并正常工作**，以证明其未被破坏。

## 10. 验收标准

**新功能：**
- 运输管理**可见入口为新的按 VIN 单车功能**；菜单中不再出现旧单据式（运输单/发车清单/行车路单/经销商行）入口。
