# 车辆阶段待办与数据修订后端接口变更清单

本次后端改造共新增 4 个车辆数据修订接口，并调整 7 个既有车辆/阶段列表接口的查询范围。未删除接口，未生成或修改前端代码。

## 1. 阶段待办列表接口调整

以下接口的路径、请求类型、返回类型和权限保持不变，只调整列表查询范围：每个列表固定查询自身当前生命周期阶段。车辆确认并推进生命周期后，立即从原阶段列表中消失，不能再通过 `CONFIRMED` 等筛选参数查询回来。

| 方法 | 路径 | 固定生命周期阶段 | 返回类型 | 权限 |
| --- | --- | --- | --- | --- |
| GET | `/api/production` | `PENDING_OFFLINE` | `Result<PageResult<VehicleListResponse>>` | `sys:vehicle:list` |
| GET | `/api/inbounds` | `PENDING_INBOUND` | `Result<PageResult<InboundResponse>>` | `vlm:inbound:list` |
| GET | `/api/allocations` | `PENDING_ALLOCATION` | `Result<PageResult<AllocationResponse>>` | `vlm:allocation:list` |
| GET | `/api/invoices` | `PENDING_INVOICE` | `Result<PageResult<InvoiceListResponse>>` | `vlm:invoice:list` |
| GET | `/api/payments` | `PENDING_PAYMENT` | `Result<PageResult<PaymentResponse>>` | `vlm:payment:list` |
| GET | `/api/deliveries` | `PENDING_DELIVERY` | `Result<PageResult<DeliveryResponse>>` | `vlm:delivery:list` |
| GET | `/api/registrations` | `PENDING_REGISTRATION` | `Result<PageResult<RegistrationResponse>>` | `vlm:registration:list` |

### 1.1 通用查询规则

- 固定生命周期条件由后端强制添加，调用方不能通过查询参数扩大范围。
- `stageStatus=DRAFT` 只查询当前生命周期内已创建但尚未确认的草稿。
- `stageStatus=CONFIRMED` 不再用于查询已经推进到后续生命周期的历史记录。
- 当前阶段尚未创建草稿的车辆仍可出现在相应待办列表中；销售分配和上牌列表也保留该能力。
- 发票列表只查询 `PENDING_INVOICE`，不再同时返回已经进入 `PENDING_PAYMENT` 的车辆。
- 其他筛选条件仍可在固定生命周期范围内进一步缩小结果。

> **接口拆分：** 生产录入待办由新接口 `GET /api/production` 承担（固定 `PENDING_OFFLINE`）。`GET /api/vehicles` 不再固定阶段，恢复为通用车辆分页查询（支持可选 `lifecycleStage`）。前端「生产录入」列表须从 `/api/vehicles` 改调 `/api/production`。

### 1.2 保持不变的阶段接口

本次未修改各阶段的详情、创建、普通编辑和确认接口路径。普通编辑接口仍只能修改未确认草稿；确认接口仍负责写入确认信息并推进车辆生命周期。

## 2. 车辆数据修订接口

接口基础路径：`/api/vehicle-corrections`

该入口用于管理员在阶段数据确认后发现录入错误时进行修订。接口查询完整车辆历史，但保存时禁止修改 VIN 和流程控制字段。

| 方法 | 路径 | 用途 | 权限 |
| --- | --- | --- | --- |
| GET | `/api/vehicle-corrections` | 分页查询完整车辆列表 | `vlm:vehicle-correction:list` |
| GET | `/api/vehicle-corrections/export` | 按当前筛选条件导出全部车辆 | `vlm:vehicle-correction:export` |
| GET | `/api/vehicle-corrections/{vehicleId}` | 查询车辆全景修订详情 | `vlm:vehicle-correction:list` |
| PUT | `/api/vehicle-corrections/{vehicleId}` | 修订已有阶段记录的业务字段 | `vlm:vehicle-correction:edit` |

新菜单及三个权限在初始化 SQL 和增量迁移中默认只授予 `ADMIN`。其他角色只有被额外授予相应权限后才能访问。

### 2.1 分页查询完整车辆列表

```http
GET /api/vehicle-corrections
```

查询参数：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `pageNum` | Integer | 否 | 页码 |
| `pageSize` | Integer | 否 | 每页数量 |
| `vin` | String | 否 | VIN 模糊查询 |
| `modelId` | Long | 否 | 车型 ID |
| `modelName` | String | 否 | 车型名称 |
| `series` | String | 否 | 车系 |
| `lifecycleStage` | String | 否 | 生命周期筛选，不设置固定阶段 |

### 2.2 导出当前筛选条件下的全部车辆

```http
GET /api/vehicle-corrections/export
```

筛选参数与分页列表相同。`vin`、`modelId`、`modelName`、`series`、`lifecycleStage`、`dealerId` 全部生效；`pageNum`、`pageSize` 仅被导出忽略，因此导出的是当前筛选条件下的全部车辆，而不是当前页。

返回类型：Excel 文件，响应媒体类型为 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`。

导出结构完整保留 `Sample of Master Sheet.xlsx` 格式：

- 工作表名称固定为 `Sheet1`。
- 第 1 行为 A:AS 共 45 列精确表头，列名、顺序、空格和单元格内换行均与样表一致。
- 第 2 行为部门分组表头，保留样表的填充色、字体、对齐和边框。
- 第 2 行合并区域为 `B2:N2`、`O2:Q2`、`R2:U2`、`V2:Y2`、`Z2:AC2`、`AD2:AG2`、`AH2:AN2`、`AO2:AS2`。
- 数据从第 3 行开始，列顺序与分页查询的 45 个可见响应字段一致。

### 2.3 查询车辆全景修订详情

```http
GET /api/vehicle-corrections/{vehicleId}
```

返回类型：`Result<VehiclePanoramaResponse>`

响应聚合以下既有数据：

1. `production`：生产信息。
2. `inbound`：入库信息。
3. `allocation`：销售分配信息。
4. `invoices`：多张发票记录。
5. `payment`：收款信息。
6. `delivery`：配送信息。
7. `registration`：上牌信息。

不存在的单条阶段记录返回 `null`，没有发票时返回空列表。车辆不存在或已删除时返回错误码 `6001`。

### 2.4 修订车辆阶段数据

```http
PUT /api/vehicle-corrections/{vehicleId}
Content-Type: application/json
```

请求示例：

```json
{
  "production": {
    "id": 101,
    "modelId": 10,
    "exteriorColorId": 20,
    "interiorColorId": 30,
    "engineNumber": "ENG-0001",
    "yearMake": "2026",
    "material": "M-01",
    "shipment": "S-01",
    "batch": "B-01",
    "offlineEpmbDate": "2026-07-01",
    "epmbOkDate": "2026-07-02",
    "remark1": "修正生产数据"
  },
  "invoices": [
    {
      "id": 201,
      "invoiceType": "INVOICED",
      "invoiceNo": "INV-202607-001",
      "invoiceDate": "2026-07-03",
      "remark": "修正发票号"
    }
  ],
  "delivery": {
    "id": 301,
    "etdToDealer": "2026-07-04",
    "etaToDealer": "2026-07-05",
    "trollyType": "4 units",
    "fullyLoad": true,
    "receivedDate": "2026-07-05",
    "deliveryStatus": "DELIVERED",
    "remark7": "修正配送数据"
  }
}
```

返回类型：`Result<Void>`

#### 请求对象字段

| 对象 | 可写字段 | 必填及长度限制 |
| --- | --- | --- |
| `production` | `id`、`modelId`、`exteriorColorId`、`interiorColorId`、`engineNumber`、`yearMake`、`material`、`shipment`、`batch`、`offlineEpmbDate`、`epmbOkDate`、`remark1` | `id`、车型、内外饰颜色、发动机号必填；`engineNumber` 最长 50，`yearMake` 最长 20，`material`/`shipment`/`batch` 最长 100，`remark1` 最长 500 |
| `inbound` | `id`、`saicBuyOffDate`、`dateToStorageYard`、`remark2` | `id` 必填；已确认记录的两个日期不能为空；`remark2` 最长 500 |
| `allocation` | `id`、`allocatedDate`、`dealerId`、`salesStatus`、`remark3` | `id`、`dealerId` 必填；状态最长 50；备注最长 500 |
| `invoices` | 每项的 `id`、`invoiceType`、`invoiceNo`、`invoiceDate`、`remark` | 每项前四个字段必填；类型最长 50，发票号最长 100，备注最长 500 |
| `payment` | `id`、`paymentDate`、`creditFullPaymentDate`、`paymentStatus`、`remark5` | `id`、`paymentDate` 必填；状态最长 50；备注最长 500 |
| `delivery` | `id`、`etdToDealer`、`etaToDealer`、`trollyType`、`fullyLoad`、`receivedDate`、`deliveryStatus`、`remark7` | `id` 必填；拖车类型最长 20，状态最长 50，备注最长 500 |
| `registration` | `id`、`drosstechStatus`、`uploadDate`、`registrationDate`、`customerRegion`、`remark8` | `id` 必填；状态最长 50，客户区域最长 100，备注最长 500 |

#### 保存规则

- 请求至少包含一个阶段对象或一条发票记录，空请求会被拒绝。
- 只更新已经存在且属于路径中 `vehicleId` 的阶段记录，不创建新阶段记录。
- `invoices` 中的记录 ID 不可重复，每张发票都必须属于路径车辆。
- 请求中出现的阶段对象按完整业务字段替换：该对象内未传入的可空字段会按 `null` 清空。
- 可空字典字段使用 JSON `null` 清空；空白字符串会被拒绝。
- 车型、内外饰颜色和经销商必须存在、启用且未删除。
- 字典字段必须是有效的 `sales_status`、`invoice_status`、`payment_status`、`delivery_status` 或 `drosstech_status` 值。
- `etaToDealer` 不能早于 `etdToDealer`，`trollyType` 只能为 `4 units` 或 `6 units`。
- 已确认的入库记录仍必须保留两个入库日期；已确认的配送记录仍必须保留签收日期。

#### 不可修改字段

以下字段不在请求白名单中，不能通过本接口修改：

- VIN。
- `vehicleId`。
- 车辆生命周期 `lifecycleStage`。
- 阶段状态 `stageStatus`。
- 发票序号 `invoiceSeq`。
- `confirmedBy`、`confirmedAt`。
- 创建人、创建时间、更新人、更新时间和删除标记。

#### 事务、锁和审计

- 先锁定车辆记录，再按请求中的阶段记录 ID 逐条加行锁。
- 所有阶段更新和成功审计处于同一事务，任一步失败都会回滚本次请求的全部更新。
- 每个阶段更新必须且只能影响一条未删除记录。
- 成功时写入“车辆数据修订-字段差异”日志，包含 `vehicleId`、VIN 以及白名单字段的 `before`/`after` 数据。
- 失败时继续使用原有 `@OpLog` 记录请求参数和异常结果。
- 修订不会触发生命周期推进，也不会覆盖原确认人和确认时间。

## 3. 新增权限和菜单

| 类型 | 名称/标识 | 说明 |
| --- | --- | --- |
| 页面菜单 | `车辆数据修订` | 路径 `/production/vehicle-correction` |
| 查询权限 | `vlm:vehicle-correction:list` | 查询完整车辆列表和修订详情 |
| 编辑权限 | `vlm:vehicle-correction:edit` | 保存车辆阶段数据修订 |
| 导出权限 | `vlm:vehicle-correction:export` | 按当前筛选条件导出完整车辆主表 |

全量初始化 SQL 和增量迁移 SQL 均默认只给 `ADMIN` 分配上述菜单和权限。增量迁移可重复执行，不会重复创建角色菜单关系。

## 4. 错误码

| 错误码 | 说明 | 常见场景 |
| --- | --- | --- |
| `400` | 请求参数错误 | 字典值无效、长度超限、日期关系不合法或请求为空 |
| `6001` | 车辆不存在 | 路径车辆不存在或已删除 |
| `6007` | 阶段数据不存在 | 请求中的阶段记录不存在、已删除或更新未影响一条记录 |
| `6018` | 修订记录与车辆不匹配 | 阶段记录不属于路径中的车辆 |

## 5. 保持不变的接口

以下接口行为不因本次数据修订入口而改变：

- 各阶段详情、创建、普通编辑和确认接口。
- `/api/panorama/{vin}` 及全景导出接口。
- `/api/transport-orders/**`、`/api/dispatch-lists/**` 和 Waybill 相关接口。

普通阶段编辑仍拒绝修改已确认记录；只有具备独立修订权限的管理入口可以修改确认后的业务字段。
