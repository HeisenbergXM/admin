- **Spec ID**：D00004
- **需求类型**：优化需求（D00003 的前端页面设计派生件）

- **上游需求**：`.cx/D00003/specs/design.md`

> 本文档面向前端开发，仅覆盖 **D00003 运输管理改造** 涉及的页面变更：新增两段「按 VIN 单车维护」的物流页面，并说明旧单据式页面的隐藏处理。其余模块（生产/销售/财务/上牌/主数据/系统管理/车辆全景视图）页面**沿用 D00002 不变**，本文档不重复。业务规则、数据模型、卡控与不回归约束以 D00003 为准。

## 2. 全局交互范式（复用 D00002，不重复）

本模块两个阶段页面**完全复用** D00002 §2 已确立的全局交互范式，前端应直接套用同一套通用组件：

- **§2.1「草稿 → 确认」两步范式与三态**（草稿态可改 / 已确认态只读 / 详情态只读）——入库、配送表单均为三态表单。
- **§2.2 卡控与按钮可用性**——前置阶段未确认时入口禁用，后端为准，提交异常需弹错误。
- **§2.3 生命周期状态徽标配色**——`PENDING_INBOUND`（蓝）、`PENDING_ALLOCATION`（蓝）、`PENDING_DELIVERY`（青）、`PENDING_REGISTRATION`（青）沿用同一组件与配色。
- **§2.4 列表页通用规范**——查询条 + 分页表格 + 行操作，每页 20 条，空态/加载态，业务列表不导出。

> 与 D00002 旧运输页面的关键差异：旧版操作对象是**单据/单据行**（整单确认、按经销商行签收），新版操作对象是**单辆车（VIN）**，即回归到与生产/销售/财务表单完全相同的「一车一表单、单车确认」范式。

## 4. 车厂 → 中转仓库（按 VIN 单车维护入库）

对应 D00003 §6.1。操作对象为单辆车：物流专员在待办列表选中一辆 `PENDING_INBOUND` 的车，进入入库表单填写并确认，确认后该车推进 `PENDING_ALLOCATION`。

**菜单名**：中转运输

| 处理状态 | 下拉 | ○ | 待处理/草稿/已确认 | t_veh_inbound.stage_status（未建记录=待处理） |

**列表范围**：默认展示处于 `PENDING_INBOUND` 的车辆（含尚未建入库草稿的「待处理」与已存草稿）；已确认车辆可通过状态筛选查看（只读）。

**行操作（按状态）**

- `待处理 / 草稿`：`[维护]` → 进入 N1.1（草稿态，可填写/续填）
- `已确认`：`[查看]` → 进入 N1.1（只读详情）

> 无「新建单据」按钮——不再有运输单概念；每辆车即一条待办，直接维护。

### N1.1 入库信息维护表单（草稿 / 确认 / 详情三态）

**用途**：维护单车「车厂→中转仓库」入库信息；`[保存草稿]` 可反复改；`[确认]` 锁定并推进 `PENDING_INBOUND → PENDING_ALLOCATION`。

```
┌───────────────────────────────────────────────────────────────────────┐
│ 入库维护   LSJW...004                        阶段：●待入库(PENDING_INBOUND)│
├───────────────────────────────────────────────────────────────────────┤
│  车辆信息（只读）  车型 ZS EV   外饰 红   内饰 灰   车型年 2023            │
│ ├─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─┤ │
│  入库信息                                                                │
│   SAIC buy off 日期 [📅__________] *                                     │
│   到中转仓库日期      [📅__________] *                                     │
│   备注2              [＝________________________________]                 │
├───────────────────────────────────────────────────────────────────────┤
│                              [取消]  [保存草稿]  [确认（不可逆）]         │
└───────────────────────────────────────────────────────────────────────┘
```

**字段表**

| 字段 | 控件 | 必填 | 校验 | 数据来源 |
|------|------|------|------|----------|
| 车辆信息(车型/外饰/内饰/车型年) | 只读文本 | — | — | 主表+主数据 |
| SAIC buy off 日期 | 日期选择 | ● | 非空、日期格式 | 用户输入（t_veh_inbound.saic_buy_off_date） |
| 到中转仓库日期 | 日期选择 | ● | 非空、日期格式 | 用户输入（date_to_storage_yard） |
| 备注2 | 多行文本 | ○ | 长度限制 | 用户输入（remark2） |

**三态行为**

- **草稿态**（无记录首次进入=空表单；已存草稿=回填）：字段可编辑；`[保存草稿]` 创建/更新 `t_veh_inbound`（`stage_status=draft`），不推进阶段；`[确认]` 弹二次确认框（"确认后不可修改，该车将进入待分配"）→ 提交成功后阶段→`PENDING_ALLOCATION`，字段转只读。
- **确认态/详情态**：所有字段只读；隐藏 `[保存草稿]`/`[确认]`；顶部显示阶段徽标 + 确认人/确认时间；底部仅 `[返回]`。

**校验与提示**

- 必填项（两个日期）未填点确认：定位首个错误字段并标红，阻止提交。
- 确认成功：toast「入库已确认，车辆已进入待分配」，返回 N1。
- 后端卡控异常（该 VIN 已不在 `PENDING_INBOUND`，如被并发推进）：弹错误提示，刷新该行状态。

**流转**：确认成功后该车退出 N1 待办范围，进入销售管理 P4 车辆销售（待分配）可操作范围（见 D00002）。

**三态行为**

- **草稿态**：字段可编辑；`[保存草稿]` 创建/更新 `t_veh_delivery`（`stage_status=draft`），不推进阶段；`[确认签收]` 弹二次确认（"确认后不可修改，该车将进入待上牌"）→ 提交成功后阶段→`PENDING_REGISTRATION`，字段转只读。

**校验与提示**

- 签收日期未填点确认签收：标红并阻止提交。
- 确认成功：toast「配送签收已确认，车辆已进入待上牌」，返回 N2。
- 后端卡控异常（该 VIN 不在 `PENDING_DELIVERY`，或未分配经销商）：弹错误提示。

**流转**：确认成功后该车退出 N2 待办范围，进入销售管理 P5 车辆上牌（待上牌）可操作范围（见 D00002）。

## 6. 旧单据式页面的隐藏处理

对应 D00003 §6.4 / §8.3。前端需保证「两套共存、旧套仅隐藏入口、可快速恢复」：

- **菜单/路由**：从菜单管理隐藏「车厂到仓库·运输单」（D00002 P2/P2.1）与「仓库到经销商·发车清单」（D00002 P3/P3.1/P3.2）的菜单项与路由入口。
- **页面组件保留**：这些页面的前端组件代码**不删除**，仅解除菜单挂载与路由注册（或以特性开关关闭），便于日后恢复。
- **不改动其它入口**：其余模块菜单、路由与页面保持不变。
- **恢复方式**：重新挂回菜单项/路由即可复原旧页面，无需回滚组件代码。

> 前端不得因隐藏旧入口而删除旧页面依赖的共享组件（状态徽标、VIN 选择器、确认弹窗、字典/主数据下拉等）——这些为新旧两套共用。

## 7. 全景视图（P8）物流分区适配

车辆全景视图（D00002 P8，仅业务主管、可导出）本身**不重绘**，仅其物流分区的数据来源调整：

- 「车厂到仓库」分区改为展示 `t_veh_inbound` 字段（SAIC buy off 日期、到中转仓库日期、备注2、确认人/时间）。
- 「仓库到经销商」分区改为展示 `t_veh_delivery` 字段（ETD/ETA、轿运车类型、是否满载、签收日期、配送状态、备注7、确认人/时间）。
- 其余分区（生产/销售/发票/收款/上牌）与时间线组件不变。

> 全景视图以新阶段表为数据源；旧单据数据是否展示见 D00003 开放问题（本期默认不展示）。

## 8. 前端开发注意事项（本模块）

1. **直接复用通用组件**：入库/配送两页都是标准「列表 + 三态表单」，应直接复用 D00002 已抽象的列表组件、三态阶段表单组件、确认二次弹窗、状态徽标——无需为运输单独造轮子。
2. **无单据概念**：不再有「新建单据 / 加入 VIN / 整单确认 / 按行签收」等交互；每辆车即一条待办，一车一表单、单车确认。列表页不出现「新建」按钮。
3. **待办列表由后端按阶段过滤**：N1 候选=`PENDING_INBOUND`，N2 候选=`PENDING_DELIVERY`，实时拉取不缓存；前置未确认的车不会出现。
4. **经销商只读联动**：配送表单经销商取自销售分配，只读展示（编码+名称），前端不提供选择/修改。
5. **前后端双校验**：前端必填校验仅为体验；确认提交后须处理后端卡控异常（阶段冲突、未分配经销商、并发推进），统一弹错误并刷新状态。
6. **旧入口隐藏可恢复**：隐藏旧运输页面仅解除菜单/路由，不删组件、不删共享依赖。
7. **导出唯一入口**：本模块列表/表单均无导出按钮（仅全景视图可导出，沿用 D00002）。

## 9. 验收要点（页面层面）

- 运输管理菜单仅显示新入口（**中转运输** / **发车清单**），旧运输单/发车清单三层入口不可见。
- N1/N1.1 入库：待办列表按 `PENDING_INBOUND` 展示；单车表单三态正确；确认弹二次确认且不可逆；确认后 `PENDING_INBOUND → PENDING_ALLOCATION`。
- N2/N2.1 配送：待办列表按 `PENDING_DELIVERY` 展示；经销商只读带出；`trolly_type`/`fully_load` 可填；确认签收后 `PENDING_DELIVERY → PENDING_REGISTRATION`。
- 两页字段的控件类型、必填、校验、数据来源与本稿字段表一致；车辆基本信息只读联动。
- 卡控在前端正确体现：非对应阶段车辆不出现在待办；提交冲突有错误提示。
- 旧运输页面组件保留、可通过恢复菜单复原；其余模块页面（生产/销售/财务/上牌/全景）与 D00002 一致未受影响。
- 全景视图物流分区正确展示 `t_veh_inbound`/`t_veh_delivery` 数据。
