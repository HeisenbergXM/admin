# 车辆阶段待办列表过滤设计

## 1. 背景与目标

车辆生命周期模块按角色分工维护生产、入库、销售分配、发票、收款、配送和上牌数据。当前部分列表允许通过阶段记录状态查询已确认历史，部分列表在未传过滤条件时也会返回不属于当前待办阶段的数据，导致操作人员看到大量已经处理完成或暂时无需处理的车辆。

本次改造将各操作页面的列表统一为“当前待办”语义：只返回当前角色在该页面需要录入、修改、确认或完成必要后续动作的车辆。阶段确认并推进生命周期后，车辆必须立即从原操作列表消失。

车辆综合查询、车辆详情和车辆全景继续承担历史查询与追溯职责，不因本次改造收窄。

## 2. 范围

### 2.1 纳入范围

- 生产录入列表
- 单车入库列表
- 销售分配列表
- 发票确认及形式发票转正列表
- 收款确认列表
- 单车配送列表
- 车辆上牌列表
- 上述列表的请求参数说明、Mapper SQL、Service 测试和 SQL 冒烟测试

### 2.2 不纳入范围

- `GET /api/vehicles` 通用车辆分页查询
- 车辆基本信息、车辆详情、车辆全景和全景导出
- 各阶段单车详情接口
- 已隐藏的旧运输单、旧发车清单及其 API
- RBAC 菜单与按钮权限配置
- 生命周期流转顺序、阶段表结构和确认写入逻辑

## 3. 设计原则

1. 阶段范围由后端接口固定，不能由调用方通过查询参数扩大。
2. 当前阶段尚未创建记录的车辆和已经保存为草稿的车辆都属于待办，均应显示。
3. 普通阶段确认后生命周期会推进，车辆因此立即从原阶段列表消失。
4. 查询条件只允许在固定待办集合内继续缩小结果，例如 VIN、车型、经销商、日期或业务状态。
5. 历史数据仍保存在阶段表中，并可通过综合查询、详情和全景能力追溯。

## 4. 固定待办范围

| 操作列表 | 接口 | 后端固定条件 | 确认后的结果 |
|---|---|---|---|
| 生产录入 | `GET /api/production` | `v.lifecycle_stage = 'PENDING_OFFLINE'` | 推进到 `PENDING_INBOUND` 后消失 |
| 单车入库 | `GET /api/inbounds` | `v.lifecycle_stage = 'PENDING_INBOUND'` | 推进到 `PENDING_ALLOCATION` 后消失 |
| 销售分配 | `GET /api/allocations` | `v.lifecycle_stage = 'PENDING_ALLOCATION'` | 推进到 `PENDING_INVOICE` 后消失 |
| 发票确认 | `GET /api/invoices` | 首次开票待办，或仍需形式发票转正的待办 | 详见 4.1 |
| 收款确认 | `GET /api/payments` | `v.lifecycle_stage = 'PENDING_PAYMENT'` | 推进到 `PENDING_DELIVERY` 后消失 |
| 单车配送 | `GET /api/deliveries` | `v.lifecycle_stage = 'PENDING_DELIVERY'` | 推进到 `PENDING_REGISTRATION` 后消失 |
| 车辆上牌 | `GET /api/registrations` | `v.lifecycle_stage = 'PENDING_REGISTRATION'` | 推进到 `COMPLETED` 后消失 |

除发票的转正例外外，列表不得仅凭阶段记录的 `stage_status` 查询跨生命周期历史记录。

### 4.1 发票列表的必要例外

发票模块包含两个业务动作，不能简单限定为一个生命周期阶段：

- 首次开票：车辆处于 `PENDING_INVOICE`。
- 形式发票转正：车辆处于 `PENDING_PAYMENT`，最新有效记录仍是已确认的 `PROFORMA_INVOICED`，且不存在已确认的正式发票。

因此发票列表只返回以下并集：

```text
lifecycle_stage = PENDING_INVOICE
OR
(
  lifecycle_stage = PENDING_PAYMENT
  AND 已确认首张发票为 PROFORMA_INVOICED
  AND 不存在已确认的 INVOICED 转正记录
)
```

首次正式发票确认后，车辆立即从发票列表消失。首次形式发票确认后，车辆仍留在列表中，但唯一相关操作变为“形式发票转正”；转正确认后车辆从发票列表消失。这符合“只展示仍有当前操作的数据”的目标。

## 5. API 与数据模型

### 5.1 新增生产待办列表

在现有 `VehProductionController` 增加：

| 方法 | 路径 | 权限 | 响应 |
|---|---|---|---|
| GET | `/api/production` | `sys:vehicle:list` | `PageResult<VehicleListResponse>` |

新增 `ProductionQueryRequest extends PageRequest`，支持 VIN、车型 ID、车型名称和车系等生产列表所需的缩小条件，不暴露生命周期阶段条件。

生产 Mapper 增加分页查询，复用车辆列表已有的车型、颜色和生产状态字段映射，但固定 `PENDING_OFFLINE`。`GET /api/vehicles` 保持原有综合查询行为。

### 5.2 现有阶段查询参数兼容

现有入库、销售分配、收款、配送和上牌请求 DTO 中的 `stageStatus` 暂时保留，避免旧前端因参数绑定或类型定义立即破坏，但其语义收窄为：

- 空值或对应的 `PENDING_*`：查询该接口的全部当前待办。
- `DRAFT`：仅在固定生命周期范围内进一步筛选已有草稿。
- `CONFIRMED` 或其他值：返回空列表，不得查询跨阶段历史。

无论传入何值，SQL 都必须首先包含该接口固定的 `v.lifecycle_stage` 条件。接口文档将 `stageStatus` 标注为兼容参数，并明确不能用于历史查询。后续前端完成迁移后可另行移除该参数，本次不做破坏性删除。

发票列表不使用通用 `stageStatus` 参数，其业务条件按 4.1 固定。

## 6. 查询实现

每个阶段 Mapper 使用显式的固定生命周期谓词作为基础条件，再叠加当前 DTO 的 VIN、车型、经销商、日期和业务状态条件。不能在 `<choose>` 的不同分支中用 `stage_status = 'CONFIRMED'` 替代生命周期条件。

销售分配和上牌列表未传 `stageStatus` 时，不再以“阶段记录存在”为默认条件，而是查询固定生命周期下的全部车辆；这样尚未创建草稿的待办车辆也可进入操作。

入库、配送、销售分配和上牌采用 `LEFT JOIN` 阶段表，保证未创建阶段记录的当前待办仍出现。已有草稿返回 `DRAFT`，未建记录返回对应的 `PENDING_*` 展示状态。

收款列表继续显示所有 `PENDING_PAYMENT` 车辆。只有形式发票、尚未转正的车辆仍属于收款阶段，因此可以显示，但现有正式发票前置校验继续阻止其确认收款。

## 7. 一致性与异常数据

生命周期是操作列表归属的唯一主依据。若历史阶段记录仍为 `DRAFT`，但车辆已不在该生命周期阶段，该记录不出现在操作列表中；数据修复应通过管理或数据库治理处理，不能为了暴露异常历史而放宽待办列表。

确认接口的事务、行锁和 `LifecycleService` 校验保持不变。列表结果只是一份当前状态快照；若用户打开页面后车辆被其他人确认，后续修改或确认仍由现有生命周期校验拒绝。

## 8. 测试设计

### 8.1 Mapper SQL 冒烟测试

为各阶段分页 SQL 验证：

- 必须包含对应的固定 `v.lifecycle_stage` 条件。
- 不存在仅按 `stage_status = 'CONFIRMED'` 查询历史的分支。
- 销售分配和上牌默认查询不再要求阶段记录已存在。
- 发票查询只包含首次开票待办和未转正形式发票待办。

### 8.2 Service 单元测试

- 新生产分页方法正确传递分页和过滤条件，并补充状态中文标签。
- 各阶段 `page*` 方法仍正确分页和填充标签。
- 非法或 `CONFIRMED` 兼容参数不能扩大结果范围。

### 8.3 集成验收场景

对每个普通阶段验证一辆车：

1. 车辆进入对应 `PENDING_*` 后出现在列表中。
2. 未创建阶段记录时仍可见。
3. 保存 `DRAFT` 后仍可见。
4. 确认并推进生命周期后，从原列表消失并出现在下一阶段待办列表中。
5. 使用 `stageStatus=CONFIRMED` 不能重新查出该车。
6. 车辆仍可在 `/api/vehicles` 和全景查询中追溯。

发票另行验证：

1. `PENDING_INVOICE` 车辆可见。
2. 首次正式发票确认后从发票列表消失。
3. 首次形式发票确认后仍作为“待转正”显示。
4. 转正确认后从发票列表消失。

## 9. 验收标准

- 七个当前使用的阶段操作列表均只展示该页面仍需处理的数据。
- 已完成当前阶段的车辆不能通过列表参数重新查询出来。
- 生产列表使用独立接口，通用车辆列表没有被收窄。
- 未建记录和草稿记录都不会从当前阶段待办中遗漏。
- 形式发票转正这一跨阶段但仍需操作的场景不被误删。
- 原有确认卡控、历史详情、全景查询和旧运输 API 行为不变。
- 新增及既有自动化测试全部通过。
