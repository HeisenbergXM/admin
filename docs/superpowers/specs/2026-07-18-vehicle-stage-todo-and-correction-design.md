# 车辆阶段待办收敛与管理修订设计

## 背景

当前部分车辆业务列表既能查询当前待办，也能通过阶段记录状态查询已确认历史。销售分配、上牌等列表在未传阶段状态时还会返回已有记录，发票列表同时包含待开票和待收款车辆。这使操作人员看到大量与当前工作无关的数据。

业务列表应采用待办语义：每个岗位只看到车辆当前生命周期正在等待其处理或确认的数据；阶段确认并推进生命周期后，该车辆立即从原岗位列表消失。历史数据仍需保留，供管理人员查询和在确认后发现录入错误时修订。

## 目标

1. 将生产、入库、销售分配、发票、收款、配送、上牌列表固定为各自生命周期阶段的待办列表。
2. 确认后的车辆不可再通过原业务列表查询，即使调用方传入 `CONFIRMED` 等历史状态筛选条件。
3. 在车辆中心新增仅管理人员可见的“车辆数据修订”菜单，保留原车辆列表的完整查询能力。
4. 允许有独立权限的管理人员修订既有阶段记录中的业务字段，但禁止修改 VIN、流程控制字段和审计字段。
5. 修订操作不改变生命周期，不重新执行确认，也不新增或删除阶段记录。

## 非目标

- 不提供车辆生命周期回退、跳转或重新确认功能。
- 不允许通过修订入口创建缺失的阶段记录、删除阶段记录或调整发票序号。
- 不修改运输单、发车清单等批量运输单据的查询语义。
- 不移除车辆全景和完整历史查询能力。
- 不在普通业务编辑接口中增加管理员绕过确认锁的逻辑。

## 业务列表查询规则

正常业务列表由后端固定叠加生命周期条件：

| 页面/接口 | 固定生命周期 | 用途 |
| --- | --- | --- |
| `GET /api/vehicles` | `PENDING_OFFLINE` | 生产录入与确认 |
| `GET /api/inbounds` | `PENDING_INBOUND` | 单车入库 |
| `GET /api/allocations` | `PENDING_ALLOCATION` | 销售分配 |
| `GET /api/invoices` | `PENDING_INVOICE` | 发票处理 |
| `GET /api/payments` | `PENDING_PAYMENT` | 收款处理 |
| `GET /api/deliveries` | `PENDING_DELIVERY` | 单车配送 |
| `GET /api/registrations` | `PENDING_REGISTRATION` | 上牌处理 |

查询仍支持 VIN、车型、经销商、日期等页面相关业务条件，但这些条件只能在固定生命周期结果集内进一步缩小范围，不能扩大范围。

为兼容现有调用方，`VehicleQueryRequest.lifecycleStage` 以及各阶段查询请求中的 `stageStatus` 暂时保留。Mapper 无论收到何种值都必须先叠加对应的固定生命周期条件；当调用方传入与页面阶段不一致的状态时返回空列表。后续前端应停止发送 `CONFIRMED`、`DRAFT` 等历史筛选值。

阶段确认继续由现有生命周期服务推进 `t_vehicle.lifecycle_stage`。事务提交后，车辆因不再满足原页面固定条件而自然从原列表消失。

## 管理修订菜单与权限

在“车辆中心”下新增“车辆数据修订”菜单。页面列表布局、分页条件和展示字段与收敛前的原车辆列表一致，可查询所有未删除车辆及其当前生命周期。

新增独立权限：

| 权限 | 用途 |
| --- | --- |
| `vlm:vehicle-correction:list` | 查看修订列表和车辆修订详情 |
| `vlm:vehicle-correction:edit` | 保存车辆业务数据修订 |

菜单和按钮使用独立的菜单记录。初始化及增量迁移脚本默认只将这两个权限分配给管理员角色；其他管理层角色可由管理员后续单独授权。普通阶段权限不能访问修订接口，修订权限也不替代普通阶段操作权限。

## 修订接口

新增独立控制器和服务，不复用普通阶段编辑接口的“未确认”校验入口：

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| `GET` | `/api/vehicle-corrections` | `vlm:vehicle-correction:list` | 完整车辆分页列表 |
| `GET` | `/api/vehicle-corrections/{vehicleId}` | `vlm:vehicle-correction:list` | 聚合读取车辆和所有既有阶段记录 |
| `PUT` | `/api/vehicle-corrections/{vehicleId}` | `vlm:vehicle-correction:edit` | 在一个事务中保存聚合修订 |

分页接口复用 `VehicleQueryRequest` 和 `VehicleListResponse` 的字段结构，但使用不带固定生命周期条件的专用 Mapper 查询，避免管理员完整查询与生产待办查询再次耦合。

详情响应包含：

- 车辆只读信息：车辆 ID、VIN、当前生命周期及标签。
- 生产记录。
- 入库记录。
- 销售分配记录。
- 发票记录列表，按 `invoiceSeq` 升序返回。
- 收款记录。
- 配送记录。
- 上牌记录。
- 每条记录的只读 ID、阶段状态、确认信息和必要的展示标签。

不存在的阶段记录返回 `null` 或空列表，编辑页显示为“尚无记录”，不得通过修订保存请求创建该记录。

## 可修订字段

修订请求按阶段使用嵌套结构。每个非空阶段对象代表需要更新一条既有记录；发票使用列表，可同时更新多条既有发票。请求必须携带阶段记录 ID，用于归属校验。

允许修订的业务字段如下：

| 阶段 | 可修订字段 |
| --- | --- |
| 生产 | `modelId`、`exteriorColorId`、`interiorColorId`、`engineNumber`、`yearMake`、`material`、`shipment`、`batch`、`offlineEpmbDate`、`epmbOkDate`、`remark1` |
| 入库 | `saicBuyOffDate`、`dateToStorageYard`、`remark2` |
| 销售分配 | `allocatedDate`、`dealerId`、`salesStatus`、`remark3` |
| 发票 | `invoiceType`、`invoiceNo`、`invoiceDate`、`remark` |
| 收款 | `paymentDate`、`creditFullPaymentDate`、`paymentStatus`、`remark5` |
| 配送 | `etdToDealer`、`etaToDealer`、`trollyType`、`fullyLoad`、`receivedDate`、`deliveryStatus`、`remark7` |
| 上牌 | `drosstechStatus`、`uploadDate`、`registrationDate`、`customerRegion`、`remark8` |

以下字段在请求模型中不存在或只读，服务不得从客户端复制：

- VIN 和车辆 ID。
- `lifecycleStage`。
- 各阶段的 `vehicleId` 和 `stageStatus`。
- `invoiceSeq`。
- `confirmedBy`、`confirmedAt`。
- `createdBy`、`createdAt`、`updatedBy`、`updatedAt`、`deleted`。

正常的 MyBatis 自动填充机制可以更新 `updatedBy` 和 `updatedAt`，但客户端不能指定它们。

## 校验、事务与并发

保存修订时执行以下步骤：

1. 校验当前用户具有 `vlm:vehicle-correction:edit` 权限。
2. 在事务内锁定未删除的车辆记录；车辆不存在时返回车辆不存在错误。
3. 对请求中每个阶段记录 ID 查询并加锁。
4. 校验阶段记录未删除、`vehicle_id` 等于路径中的 `vehicleId`；任何不匹配均拒绝整个请求。
5. 校验车型、内外饰颜色、经销商仍为有效主数据；字典字段必须为对应字典中的有效值。
6. 执行现有字段长度、必填值和日期业务校验。修订已确认记录时仍不得保存会使记录不完整的数据。
7. 仅复制白名单业务字段并更新记录。
8. 任一校验或更新失败时回滚全部修订。

锁定车辆和本次请求涉及的阶段记录，可避免两个管理人员同时修订造成部分覆盖。接口不调用 `assertStage`、`assertNotConfirmed`、`confirmAndAdvance` 或 `advanceStage`，因此不会改变流程位置或确认事实。

## 操作日志

修订保存接口使用独立操作日志类型或明确的“车辆数据修订”操作名称。日志至少记录：

- 车辆 ID 和 VIN。
- 操作用户和操作时间。
- 请求涉及的阶段和记录 ID。
- 变更前后的业务字段值，或能够还原差异的结构化变更内容。
- 请求成功或失败结果。

日志不得记录认证凭证等敏感信息。修订日志与阶段记录自身的 `confirmedBy`、`confirmedAt` 分离；修订不会覆盖原确认人和确认时间。

## 错误处理

| 场景 | 处理 |
| --- | --- |
| 无列表或编辑权限 | Spring Security 返回 403 |
| 车辆不存在或已删除 | 返回车辆不存在业务错误 |
| 阶段记录不存在或已删除 | 返回阶段记录不存在业务错误 |
| 阶段记录不属于路径车辆 | 返回请求数据不匹配业务错误，不泄露其他车辆详情 |
| 主数据或字典值无效 | 返回对应字段校验错误 |
| 请求包含不可编辑字段 | DTO 不接收；若开启未知字段严格校验则返回 400 |
| 并发或数据库更新失败 | 回滚事务并返回统一业务/系统错误 |

## 数据库与菜单迁移

完整初始化脚本和增量迁移脚本都要增加新菜单、按钮权限和管理员角色授权。增量脚本必须幂等：通过稳定的菜单 ID 或权限标识检查后插入，并避免重复角色菜单关系。

本功能不新增业务表字段。若现有操作日志无法保存字段级差异，则应在实现计划中选择扩展现有日志载荷或新增专用修订日志表；无论采用哪一种，都不能把差异审计省略为只有接口路径的访问日志。

## 测试策略

### 待办列表

为七个业务列表增加 Mapper 或 SQL 冒烟测试：

- 当前生命周期车辆可见。
- 车辆确认推进到下一生命周期后不可见。
- 已确认阶段记录即使与筛选参数匹配也不可见。
- `CONFIRMED`、`DRAFT` 或其他不一致状态参数不能扩大查询范围。
- VIN、车型、经销商和日期等业务筛选仍在固定生命周期内生效。

### 修订服务

- 管理员可在单事务中更新多个已存在阶段的业务字段。
- 已确认记录可以修订，但生命周期、阶段状态和确认信息保持不变。
- VIN 和其他保护字段无法通过请求修改。
- 阶段记录 ID 属于其他车辆时拒绝请求。
- 阶段记录缺失时不能借修订入口创建。
- 无效车型、颜色、经销商或字典值被拒绝。
- 一车多张发票可按记录 ID 正确更新，发票序号不变。
- 中途任一更新失败时，之前的更新全部回滚。

### 权限与迁移

- 无权限用户访问详情和保存接口分别返回 403。
- 管理员默认获得新菜单及 list/edit 权限。
- 普通业务角色默认不获得新权限。
- 完整初始化脚本和增量迁移脚本均包含幂等、唯一的菜单数据。

最后运行完整 Maven 测试，确认现有阶段保存、确认和生命周期推进逻辑不受影响。

## 前端契约

本仓库负责后端和菜单数据；前端实现需遵循以下契约：

- 原车辆列表改为生产待办视图，只展示 `GET /api/vehicles` 返回的待生产确认车辆。
- 新“车辆数据修订”列表复用原车辆列表的筛选和表格布局，数据源改为 `/api/vehicle-corrections`。
- 仅拥有 edit 权限时显示“编辑”按钮。
- 编辑页按阶段分区显示详情；不存在的阶段只显示“尚无记录”，不提供新增按钮。
- VIN、生命周期、阶段状态、发票序号、确认信息和审计信息始终只读。
- 保存成功后重新加载详情和列表，确保展示数据库最终结果。

## 验收标准

1. 普通操作人员在每个业务列表中只能看到车辆当前生命周期对应的待办。
2. 任一阶段确认成功后，车辆不再出现在该阶段列表中，且无法通过状态参数重新查出。
3. 管理员可在新菜单查询所有未删除车辆并打开聚合修订详情。
4. 管理员可修订已存在阶段的业务字段，VIN 和所有流程、确认、审计字段保持不变。
5. 普通角色无法查看新菜单或调用修订接口。
6. 每次修订具有可追溯的字段级操作日志。
7. 所有新增测试及现有完整测试通过。
